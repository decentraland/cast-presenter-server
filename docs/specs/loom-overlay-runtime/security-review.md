# Security review — loom-overlay-runtime

Generated by the plan-plus reviewer contract with the **security** lens. Reviewed checkout: `.worktrees/loom-overlay-runtime/run` at HEAD `b2a6209` (base `2c6cdd1`). The review was read-only: no shell, git, or network access was used.

## Review summary

- The authorization path for `presentation:overlay:update` is sound:
  - It goes through the unchanged presenter check at `src/adapters/livekit-publisher/component.ts:216-260`.
  - The payload validation at `src/logic/presentation-manager/component.ts:132-146` rejects non-numbers, `NaN`, `±Infinity` and unknown sizes, and it clamps `x`/`y`. The overlay is merged through a fixed-key patch, so there is no path for prototype pollution.
- The I420 blend (`src/adapters/camera-overlay/component.ts:42-82`) stays in bounds for every caller, and the buffer sizes agree with `i420FrameSize`. Details are under Review coverage.
- One **Medium** resilience/availability defect:
  - If one camera frame throws while it is being processed, the pump stops reading but never cancels the reader.
  - rtc-node's `VideoStream` has no backpressure, so decoded frames then build up without limit until the camera goes inactive or the session stops.
  - The bubble also freezes, because `isActive()` stays `true`.
- One **Low** defect: the camera frame is converted to RGBA *before* its dimensions are checked, which contradicts the spec guardrail at `plan.md:44`.
- Blocking threshold is `medium`. **Blocking findings: 1 (Medium).**

## Verified findings

### [MEDIUM] Camera pump dies on a per-frame exception without releasing the stream: unbounded frame queue and a frozen bubble

- **Location:** `src/adapters/camera-overlay/component.ts:133-146` (pump), `:103-121` (acceptFrame), `:180-191` (start). Related: `node_modules/@livekit/rtc-node/dist/video_stream.cjs:39-49,77-83`.
- **Symbol:** `createCameraOverlay` → `pump`, `acceptFrame`, `overlay.start`.
- **Category / CWE:** Availability / resource exhaustion. CWE-400 (Uncontrolled Resource Consumption), CWE-755 (Improper Handling of Exceptional Conditions). Correctness side effect: a stale bubble.
- **Invariant:** while an overlay owns a `VideoStream`, that stream is either being drained or cancelled. `isActive()` is `true` only while live frames are arriving.
- **Observed behaviour:**
  - `pump` wraps the whole `while` loop in one `try/catch` (`:134-145`). Four calls in `acceptFrame` can throw, and the dimension check does not guard any of them:
    - `event.frame.convert(...)` (`:104`). This is an FFI request, and `video_frame.cjs:99` rethrows the FFI error case.
    - `new ImageData(...)` (`:116`), which throws when the data length does not match the dimensions.
    - `createCanvas` (`:112`), whose allocation can fail at up to 7680×7680.
    - `putImageData` (`:121`).
  - Any of these throws exits the loop permanently. The catch only logs.
  - After that throw:
    - `reader` still points at the dead pump's reader, and `running` stays `true`. Nothing cancels the reader.
    - `VideoStreamSource.onEvent` keeps calling `controller.enqueue` on every native `frameReceived` (`video_stream.cjs:42-49`). It ignores `desiredSize`, and `VideoFrame.fromOwnedInfo` copies each full decoded frame into JS memory.
    - The listener is detached only in `cancel()` (`:77-83`) or on `eos`.
    - With no reader, the `ReadableStream` queue grows by one full frame per camera frame. At 720p30 I420 that is about 1.4 MB × 30/s ≈ 40 MB/s, and it continues until `stop()`/`start()` runs (camera muted or unpublished, or the session stopped).
  - If a frame had already been accepted, `hasFrame` stays `true` and `isActive()` returns `true` (`:213-215`):
    - every output path keeps stamping the last cached camera image;
    - idle output stops being camera-driven, and the heartbeat repeats the last stamped frame.
  - A related gap in `start()` (`:181-190`):
    - the old reader is cancelled and `reader` is nulled *before* `new VideoStream(track)`;
    - if the constructor's FFI request throws (the camera handler catches it at `presentation-manager/component.ts:363-377`), `running` and `hasFrame` keep their previous values;
    - the result is the same state: active, but with no pump.
    - The publisher has already recorded `activePresenterCameraSid` (`livekit-publisher/component.ts:104`), so that track never retries.
- **Root cause:** error handling is scoped to the pump's lifetime instead of to each frame, and pump exit has no teardown.
- **Realistic impact:** one bad frame, or a transient FFI or allocation failure, drives unbounded memory growth. That ends in an OOM of the whole process, and all concurrent sessions (up to `MAX_CONCURRENT_PRESENTATIONS`) go down with it. Until then, viewers see a frozen presenter image.
  - The trigger is a remote, presenter-controlled media stream processed by native code. This review did not show that a specific frame reliably makes `convert` or the canvas throw (see Needs verification).
  - The missing teardown itself is verified. The fix is trivial.
- **Minimal proposed patch (text):**
  - In `pump`, move the `try/catch` inside the loop around `acceptFrame(value)`: log and `continue`, so one frame's failure never ends the read loop. Keep an outer `try/catch/finally` for `read()` rejections.
  - In the `finally`, if `isCurrent(ownReader)` is still true, set `running = false`, `hasFrame = false`, `reader = null`, and call `ownReader.cancel().catch(() => undefined)`.
  - In `start()`, set `running = false` and `hasFrame = false` before `new VideoStream(track)`, so a throwing constructor leaves the overlay inactive rather than stale.
- **Local regression test (`test/unit/camera-overlay.spec.ts`):**
  - **Case 1:** the mocked reader yields frame A, then frame B whose `convert` throws, then frame C, advancing `Date.now` by at least 50 ms between them. Assert that `onCameraFrame` fires for A and for C (the pump survived) and that `reader.cancel` was not called.
  - **Case 2:** `read()` rejects. Assert that `reader.cancel` was called and that `isActive()` is `false`.
  - **Case 3:** the `VideoStream` constructor throws on a second `start()`. Assert that `isActive()` is `false`.
- **Scope:** in scope. It only touches `src/adapters/camera-overlay/component.ts` and its spec.

### [LOW] Camera frame is converted to RGBA before its dimensions are validated

- **Location:** `src/adapters/camera-overlay/component.ts:104-110`.
- **Symbol:** `acceptFrame`.
- **Category / CWE:** CWE-770 (Allocation of Resources Without Limits or Throttling). Order of validation. Violates the spec guardrail at `plan.md:44` ("An invalid frame … never allocates a canvas or buffer").
- **Invariant:** remote-controlled dimensions are validated before any allocation derived from them.
- **Observed behaviour:**
  - `event.frame.convert(VideoBufferType.RGBA)` runs first. It allocates a native RGBA buffer of `w*h*4` bytes and copies it into JS.
  - Only then does `validateMediaDimensions(rgba.width, rgba.height, …)` run.
  - `event.frame.width` and `event.frame.height` are already available (`video_frame.cjs:27-31`), so the check can come first.
- **Root cause:** the check was placed after conversion, on the converted frame.
- **Realistic impact:** limited.
  - The decoder has already produced the I420 frame at those dimensions, and throttling runs this at most 20 times per second.
  - The only remote party is an authorized presenter (`livekit-publisher/component.ts:96-104`). An oversized frame costs about 2.7× more transient memory than the decoded I420 before it is rejected.
  - Below the cap there is also a second full copy at `:117` (`rgba.data.buffer.slice`).
- **Minimal proposed patch (text):**
  - Call `validateMediaDimensions(event.frame.width, event.frame.height, 'camera-overlay')` before `convert`, and return on failure with the existing `logger.warn`.
  - Optionally drop the extra copy at `:117` by wrapping `rgba.data` in `new Uint8ClampedArray(rgba.data.buffer, rgba.data.byteOffset, rgba.data.byteLength)`. `convert` returns an owned buffer via `copyBuffer`, so this is safe.
- **Local regression test:** feed a frame whose `width` is 8000. Assert that `convert` was never called and `logger.warn` was.
- **Scope:** in scope (same file).

## Needs verification

- **What makes `acceptFrame` throw in production.** Can a presenter-published stream make rtc-node 1.1.0's `convert(RGBA)` return an FFI error, or make `@napi-rs/canvas` 1.0.9's `createCanvas` or `putImageData` throw? Candidates are a large but valid frame (for example 7680×4320) under memory pressure, or unusual buffer types. The answer decides whether the Medium finding can be triggered on purpose or only by accident.
- **`TrackUnsubscribed` after a local `setSubscribed(false)`.** When a presenter is removed from room metadata, deactivation relies on `applyPresenterSubscription(participant, false)` (`livekit-publisher/component.ts:122-144`) causing `RoomEvent.TrackUnsubscribed` (`:279-286`). If rtc-node 1.1.0 does not emit it for a local unsubscribe, or if `setSubscribed` fails (it is only logged), the demoted presenter's camera keeps being stamped onto the broadcast. The publisher is unchanged, but this path now controls a pixel region on every output frame.
- **`pushFrame` can throw.** `VideoSource.captureFrame` goes through FFI. If it can throw, the `onEnd`/`onError` async callbacks reach it through `setupSlideOutput` → `pushIdleFrame` without any catch:
  - the chain runs `presentation-manager/component.ts:892-923`, then `:239-254`, then `:252`;
  - the compositor calls these callbacks without handling their promise (`video-compositor/component.ts:340-342,702`);
  - under `--unhandled-rejections=strict` (`Dockerfile:53`), a rejection there would abort the process.

  This predates the change; phase 3 wraps only `stamp`.
- **pdfjs-dist 6.3.289 in Node.** It is unknown whether the legacy build's standard-font, CMap or wasm (JPX/JBIG2) factories read only package-local files. `getDocument` at `pdf-renderer/component.ts:56` passes no `standardFontDataUrl`, `cMapUrl`, `wasmUrl` or `isEvalSupported`, and this review could not trace pdfjs internals to confirm there is no fetch path.

## Hardening opportunities

These are not blocking.

- **Tighten the camera dimension cap.** `validateMediaDimensions` defaults to a maximum of 7680 (`video-compositor/component.ts:52`). That lets each session keep a `fullCamCanvas` of up to about 236 MB (`camera-overlay/component.ts:111-115`), plus two transient copies of that size per accepted frame. The bubble is at most `0.25 × 960 = 240` px. Passing `max = 1920` (or 4096) from `acceptFrame` bounds memory per session at 10 concurrent sessions. This changes the spec's security policy, so it needs `replan`.
- **Defence in depth in `overlayRect`.** An unknown `layout.size` gives `d = NaN`, and `NaN < 2` is false (`camera-overlay/component.ts:31-32`), so the result is NaN geometry and `createCanvas(NaN, NaN)`. Today this is unreachable because `parseOverlayUpdate` validates `size`. Use `if (!(d >= 2))`, or validate `size` in `setLayout`.
- **Monotonic throttle clock.** `Date.now()` (`:138`) freezes the bubble for the whole duration of a backwards wall-clock step. `performance.now()` avoids that.
- **Explicit deactivation when a presenter is removed.** Record the owner identity of the active camera. In `RoomMetadataChanged`, call `deactivatePresenterCamera()` directly when that identity is removed, instead of relying only on the unsubscribe round-trip (`livekit-publisher/component.ts:181-206`).
- **Missing test for presenter gating.** No unit test asserts that a non-presenter `presentation:*` message is dropped before `dataHandler` (`livekit-publisher/component.ts:255-260`). The new overlay command depends entirely on that check. Add one case to `test/unit/livekit-publisher.spec.ts`.
- **Unbounded slide height (existing, out of scope).** `pdf-renderer/component.ts:64-70` fixes the width at 960 but derives the height from the page aspect ratio with no upper bound. The new idle path adds a full `rgbaToI420` copy of that frame (`presentation-manager/component.ts:234`). Cap the height, for example with `validateMediaDimensions`.
- **pdfjs options.** Pass `isEvalSupported: false` to `getDocument` as a cheap defence-in-depth setting on the upgraded parser.

## Review coverage

Tracks were covered in this order:

1. **Identity and permission boundaries.**
   - Checked data-channel gating (`livekit-publisher/component.ts:208-270`): identity from the signed LiveKit participant, presenters from room metadata, lowercase match.
   - Checked camera selection (`:91-114`, `:272-316`): camera source only, not muted, presenter only, first sid wins.
   - `overlay:update` has no separate path that bypasses these checks (`presentation-manager/component.ts:395-441`).
   - The handler is registered before `connect` and cleared on both the failure path and the stop path (`:363-377`, `:528-530`, `:1012-1013`).
2. **External data and system boundaries.**
   - `parseOverlayUpdate` (`:132-146`) and `setLayout` clamping.
   - Camera frame dimensions (`camera-overlay/component.ts:103-121`), which led to the Low finding.
   - `overlayRect` arithmetic and the `blendPatch` bounds:
     - Y writes are guarded by `0 ≤ fx < width` and `0 ≤ fy < height`.
     - UV writes are guarded by `< uvW` and `< uvH`, and `uvW = (w+1)>>1` matches `rgbaToI420` and `i420FrameSize`.
     - Patch reads stay below `d²` because `d` is even and the patch key includes `rect.d`.
     - JS typed arrays drop out-of-range stores in any case, so memory corruption is not possible from JS.
   - Buffer and dimension agreement for every caller:
     - `pushIdleFrame` gets `baseAsI420` together with `baseFrame.width/height`;
     - `decorateFrame` gets `frameCopy` sized `i420FrameSize(slideWidth, slideHeight)`.
   - ffmpeg argv: the camera input is removed (`video-compositor/component.ts:473-506`), and the filter params are still validated (`:431-434`).
   - Dependency pins: `package.json:57-65` pins rtc-node 1.1.0, canvas 1.0.9 and pdfjs 6.3.289. pdfjs 6 contains the CVE-2024-4367 fix (≥4.2.67).
   - `pdf-renderer` API changes (`:56,73,136`).
   - `create-presentation-handler.ts` no longer reads overlay fields.
3. **Correctness, concurrency and resilience.**
   - Camera active/inactive interleavings with `stop()`/`start()` ownership (`isCurrent`).
   - `stopSession` ordering, and clearing of the throttle timer (`:990-993`).
   - Pause, end and error transitions: `pushIdleFrame` is gated on `getIsPlaying`.
   - Heartbeat replacement (`livekit-publisher/component.ts:345-350`).
   - Unhandled rejections on the data, camera and timer paths: all are caught.
   - rtc-node `VideoStream` backpressure, which led to the Medium finding.

Not covered: the PPTX renderer, the network validator, the file provider, and live runtime behaviour (the manual smoke was skipped per `learnings/phase-4.json`).
