## Prior findings

### `f-bbd736635e088b5b` [MEDIUM] Camera pump dies on a per-frame exception without releasing the stream — **Resolved**

**1. Per-frame isolation.** `acceptFrame(value)` now runs inside its own `try/catch` in the loop (`src/adapters/camera-overlay/component.ts:142-146`).

- A throw from `convert`, `createCanvas`, `new ImageData` or `putImageData` is logged, and the loop continues reading.
- Callbacks were already isolated one by one (`:125-131`).
- The throttle timestamp is set before `acceptFrame` (`:141`), so failing frames are also limited to 20 per second.
- Frames that are throttled out are still read and dropped (`:140`), so the queue is drained at the rate frames arrive.

**2. Every exit path cancels the reader it owns.** The code only ever cancels a reader after it has left the single `reader` slot. Each exit path is covered:

| Exit path | Who cancels the reader |
|---|---|
| `done` (eos) at `:138` | The pump's teardown runs (`:151-157`) and calls `ownReader.cancel()`. The source has already removed its listener on eos (`video_stream.cjs:51-58`). |
| `read()` rejects (`:148-150`) | The same teardown runs. See Needs verification: on an errored stream, `cancel` does not reach the source. |
| `!isCurrent(ownReader)`, at the loop head (`:136`) or after a read (`:138`) | `isCurrent` is `running && reader === ownReader`. The only writers of `reader` and `running` are `start` (`:193-208`), `stop` (`:214-222`) and the pump's own teardown. Each one cancels the reader it removes: `start` calls `old?.cancel()` at `:195`, `stop` calls `old?.cancel()` at `:222`, and the teardown cancels at `:157`. So a pump that stops being current always owns a reader that someone else has already cancelled. |

- `reader.cancel()` on a locked, readable `VideoStream` calls `VideoStreamSource.cancel` (`video_stream.cjs:77-83`). That removes the FFI listener and disposes the native handle, so `enqueue` stops.

**3. A replaced pump cannot clobber the new reader's state.**

- The teardown is guarded by `if (reader !== ownReader) return` (`:151`). After `start()` or `stop()`, `reader` is either the new reader or `null`, so a stale pump returns without writing `running`, `hasFrame`, `patch` or `stream`.
- Between `await ownReader.read()` and `acceptFrame`, the code re-checks `isCurrent` (`:138`). `acceptFrame` is synchronous, so a stale pump cannot interleave a write to `fullCamCanvas` or `cameraSeq` after it has been replaced.
- Reader objects have unique identity, so there is no ABA hazard.

**4. `start()` constructor failure.**

- `running` and `hasFrame` are cleared before `new VideoStream(track)` (`:196-197`).
- A throw is caught, `stream` is set to `null`, a warning is logged, and `start` returns (`:199-206`). `isActive()` is therefore `false` (`:233-235`).
- The old reader was cancelled beforehand (`:195`).
- The FFI request inside the `VideoStreamSource` constructor runs before its `.on(...)` registration (`video_stream.cjs:65-72`), so a throwing request cannot leak a listener.

**5. Tests.** `test/unit/camera-overlay.spec.ts` (repair diff, around lines 442-512) covers all three cases the prior report asked for:

- `convert` throws, and the next frame is still delivered;
- `read()` rejects, the overlay becomes inactive, and the reader is cancelled;
- the constructor throws on restart, `start` does not throw, and the overlay becomes inactive.

**Residual:** after the pump deactivates itself, the idle heartbeat keeps the last stamped frame. This is tracked as the new Low below. It is a correctness defect, not a queue or memory issue.

### [LOW] Camera frame is converted to RGBA before its dimensions are validated — **Resolved**

- `validateMediaDimensions(event.frame.width, event.frame.height, 'camera-overlay')` now runs first (`src/adapters/camera-overlay/component.ts:105-110`). The frame is not converted until `:111`.
- `validateMediaDimensions` (`src/adapters/video-compositor/component.ts:52-59`) rejects non-integer, zero and oversized values, so `NaN` and `undefined` are rejected too.
- `convert` sends the source frame's own `width` and `height` to FFI (`node_modules/@livekit/rtc-node/dist/video_frame.cjs:82-96`) and does not scale. So validating the source dimensions is equivalent to validating the RGBA result.
- No canvas, `ImageData` or RGBA buffer is allocated before the check.
- The regression test asserts that `convert` is never called for a 99999-wide frame and that a warning is logged.
- The I420 copy that rtc-node makes in `fromOwnedInfo` (`video_frame.cjs:62-69`) happens before this code runs and is outside its control. The prior report already noted this.

## Verified new findings

### [LOW] Self-deactivation of the overlay does not refresh idle output; the heartbeat keeps broadcasting the last stamped bubble (correctness)

- **Location:** `src/adapters/camera-overlay/component.ts:151-157` (pump teardown) and `:199-206` (`start` failure). Related: `src/logic/presentation-manager/component.ts:239-265`, `:363-377`.
- **Category:** correctness. This is a leftover of the prior finding's "frozen bubble" side effect, not a security boundary issue. The pixels shown belong to the already-authorized presenter's own camera.
- **Invariant:** once `isActive()` becomes `false`, idle output reverts to the plain base frame.
- **Observed behaviour:**
  - The camera handler reverts idle output only on an explicit `inactive` event: it calls `overlay.stop()` and then `refreshIdleOutput(session)` (`presentation-manager/component.ts:369-371`).
  - When the pump deactivates itself (after eos or a `read()` rejection), or when a same-sid re-`start()` fails, `running` becomes `false`, but nothing notifies the manager.
  - The heartbeat last armed by `pushIdleFrame` (`:252-253`) keeps repeating the stamped frame with the frozen bubble. This lasts until the next `refreshIdleOutput`, which happens on a slide change (`:292`), at `:967`, or on a later `inactive` event.
  - `decorateFrame` (`:856`) and `stamp` (`camera-overlay/component.ts:238`) do stop stamping correctly.
- **Reachability:** not proven.
  - The eos path probably coincides with `TrackUnsubscribed`, which does call `stop` and then refresh (`livekit-publisher/component.ts:279-286`).
  - `read()` rejection is probably unreachable (see Needs verification).
  - The `start` failure only produces stale output when `start` is re-fired for the same sid while the heartbeat is already stamped.
- **Minimal remediation:** give `ICameraOverlay` an `onInactive` callback, or fire the existing `onCameraFrame` callbacks, on self-deactivation. In the manager, map it to `refreshIdleOutput(session)`. Test: after `read()` rejects, assert that `publisher.startHeartbeat` was last called with the base buffer.
- **Scope:** in scope. It touches the camera-overlay component, a single registration in the presentation manager, and the specs.

### [INFORMATIONAL] A persistent per-frame failure leaves the last good frame displayed, with a warning logged on every accepted frame

- **Location:** `src/adapters/camera-overlay/component.ts:142-146`, `:123`.
- **What happens:** if every frame fails after one good frame (for example, `convert` returns an FFI error from then on), `hasFrame` stays `true` and the bubble shows the last good image indefinitely.
- **Logging cost:** each failure logs a `warn`, bounded to 20 per second per session by the throttle (`:139-141`), so up to about 200 lines per second at 10 sessions. This is bounded, but it can drown out other logs.
- **Suggested hardening:** count consecutive failures, and after N of them tear down the pump the same way `:152-157` does. Alternatively, rate-limit the warning.

### [INFORMATIONAL] The full-size camera canvas is kept after self-deactivation

- **Location:** `src/adapters/camera-overlay/component.ts:151-157`.
- **What happens:** the teardown clears `patch` but not `fullCamCanvas`. `stop()` does clear it (`:219`). Memory stays bounded at one canvas per session, up to the 7680² cap noted in the prior report's hardening section, and is released on the next `start` of a different size or on `stop`.
- **Suggested hardening:** set `fullCamCanvas = null` in the teardown to match `stop()`.

## Needs verification

- **Can `ownReader.read()` reject in rtc-node 1.1.0?**
  - Evidence so far: `VideoStreamSource` never calls `controller.error`, its `start` does not throw, and it has no `pull` (`video_stream.cjs:27-84`). So the stream seems to never become errored, and the `read()` rejection path covered by the new test is synthetic.
  - If the stream *can* become errored, `reader.cancel()` on it rejects without calling `source.cancel`. The FFI listener would then stay registered, and each later `frameReceived` would call `enqueue` on an errored stream, which throws a `TypeError` inside the FFI event emitter.
  - Whether that throw surfaces as an uncaught exception, which would be fatal under `--unhandled-rejections=strict` / default uncaught handling, depends on how `FfiClient` emits. This review did not trace that.
- **Does eos always come with `TrackUnsubscribed`?** This decides whether the new Low is reachable on the eos path.
- **Carried over unchanged from the prior report:** the `TrackUnsubscribed`-after-local-`setSubscribed(false)` question, `pushFrame` throwing on the idle callbacks, and the pdfjs Node resource factories. The repair did not touch these.
